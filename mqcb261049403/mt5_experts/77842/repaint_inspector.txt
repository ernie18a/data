Measures whether an indicator repaints, instead of taking the claim on trust. It attaches to a chart, re-reads the buffers of the indicator under test on bars that have
already closed
, and counts every change it sees there: values that move, values that appear and values that disappear — together with the furthest point back in history at which that still happens.
Examples\ZigZag(12,5,3) on XAUUSD M1. The panel was photographed at 1 h 25 min 12 s of the run, 87 seconds before it was stopped, which is why the totals in the table below are slightly higher. Panel colours were set to black on white for the screenshot; the defaults are light text on a dark panel.
The problem
"Non-repainting" is the most frequent claim in indicator descriptions and the one that is hardest to check. The usual test is to look at the chart, remember roughly where the arrows were, reload the indicator and look again. That test misses the two cases that actually cost money.
The first is a value on a bar that closed some time ago changing while the chart stays open. The eye does not catch it: the arrow moves by a few pixels, or it is removed while attention is on the right edge of the chart.
The second is an indicator that behaves while it lives and publishes a different history after it is reloaded, which is exactly what a timeframe switch, a terminal restart or a fresh chart does to the user.
Both are measurable. What is needed is something that writes down what the indicator published the first time it published it, and then keeps checking.
What it measures
A bar is identified by its
open time
, never by its shift, so new bars, scrolling and history refills cannot be mistaken for a change.
Only closed bars are compared, shift 1 and higher. The bar that is still forming changes by definition and says nothing about repainting.
The first value seen for a closed bar becomes the reference. Every later reading is compared with the previous reading, which counts an event, and with the first reading, which measures the drift.
Three kinds of event are counted separately, because they are not equally bad:
Changed
— a value moved to a different value.
Appeared
— an empty slot received a value, so a signal materialised on a bar that was already closed.
Vanished
— a published value was erased. This is the worst kind: the signal a trader acted on is no longer in the history the next reader sees.
The headline number is
MaxShift
, the largest shift at which any event was ever seen. An indicator that only redraws the last closed bar is a different animal from one that rewrites fifteen bars of history.
Every event is written to a CSV file with the bar time, the buffer, the shift at detection and the old and new value, so the report can be audited instead of believed.
The indicator under test is created with IndicatorCreate from a parsed parameter list, so any custom indicator can be inspected without editing or recompiling anything. The parsed parameters are printed to the journal at start, which makes a wrong parameter list visible instead of silent.
Optionally the handle is released and created again every N minutes. The recorded history is deliberately
not
reset, so the run also catches the indicator that is quiet while it lives and publishes a different past after a reload.
A check is discarded, and counted as skipped rather than as evidence, whenever the indicator handle does not exist yet, the indicator is not calculated yet, there are fewer closed bars than the depth asked for, a buffer cannot be copied, or the series moves between reading the times and reading the values.
It samples: a value that exists for less time than the check interval can be missed. That is a real limit and there is a measurement of it further down.

In one trading day the ZigZag deleted 342 values it had already published on bars that were closed at the time, and one of those deletions happened 28 bars after the bar in question had closed. Three values appeared on already-closed bars. Only one of the three was a value coming back: bar 17:06 lost 4126.184, got exactly the same number back twenty seconds later, and lost it again a minute after that. That is also why Max |delta| reads 0.00000000 for the run; it is a measurement, not a gap.
The 345 events of that day by the shift at which they were detected. Most repainting is one or two bars back, which is why watching only the last closed bar is not enough.
Examples\Custom Moving Average(13,0,2), same symbol and same run window as the ZigZag above: 1 291 114 comparisons at the moment of the screenshot and not one changed value. The comparison count is printed next to the verdict on purpose — STABLE is only worth the number beside it.
What "Treat 0.0 as no value" changes, and how big the sampling gap is
The fourth copy ran the same ZigZag with that switch off, so 0.0 counts as an ordinary value: 1 308 513 comparisons, 18 + 3 + 11 = 32 events, all of them Changed, the same MaxShift of 15, and a Max |delta| of 4184.08800000 on the main buffer. That number is the gold price, because the "change" is a peak being replaced by 0.0. Both settings describe the same repainting; the default names it correctly.
The two copies did not see exactly the same list, and that is worth knowing. The fourth copy logged two events the first one missed: bar 03:32:00 on buffers 0 and 2, detected at 03:33:01. The two copies started 14 seconds apart, and the value existed for less than one check interval, so one of them sampled it and the other did not. With a one-second interval on M1, that is the resolution of the instrument.
The same ZigZag read with 0.0 counted as a value. Every deletion now shows up as Changed with a delta the size of the price. Useful as a cross-check, misleading as a description.
Audit of the numbers
The counters were not taken on trust either. An independent Python re-implementation of Examples\ZigZag, run over the raw candles fetched from the terminal, was compared with the event files:
Live run: for every one of the 17 bars where the plotted buffer lost a value, that value is absent from the replay today, and for all 17 the tool's last reading equals the replayed value.
Tester run: 343 bars with events, the same two checks, no mismatch — 341 lost values absent from the replay, and 343 of 343 last readings equal to it.

An empty value is written as EMPTY and an undefined difference is left blank, so no reader can mistake a missing number for a zero. A second file, <name>_summary.csv, holds one row per buffer with every counter plus the indicator, its parameters, symbol, timeframe and depth, refreshed every 15 seconds while the run is going, so the numbers can be recounted from the event file without parsing a log. The journal gets the start block, the first 20 events in full, and the summary above when the tool is removed.
How to use it
Put the indicator you want to check in MQL5\Indicators and note its parameter list.
Attach Repaint Inspector to a chart of the symbol and timeframe you actually trade, fill in the path and the parameters, and set the number of buffers.
Let it run over the hours you trade. Repainting is a property of market activity, not of the clock, and a quiet Sunday evening proves nothing.
Read MaxShift first, then the split between Changed, Appeared and Vanished, then open the CSV and look at a few rows.
If the indicator survives that, set the handle reload to 30 minutes and run it again.
Limits, stated plainly
The tool cannot prove the absence of repainting. It can only fail to find any over the period measured, which is why the comparison count stands next to every verdict.
It samples at the check interval. A value that comes and goes inside one interval can be missed, and the measurement above shows that happening twice in an hour and a half.
It measures what an indicator publishes through its buffers. An indicator that draws objects on the chart instead of filling buffers is invisible to it.
The Strategy Tester is useful here because it compresses a day into seconds, but a tester repaint and a live repaint are not automatically the same thing. When the answer matters, run it live.
In the Strategy Tester the indicator under test has to be present and compiled before the run starts. The tester treats a failed IndicatorCreate as a critical error and unloads the expert, which no error handling inside the tool can change: measured with a deliberately wrong path, creating the handle in OnInit gives "indicator create error" then "OnInit critical error", and creating it at the first check instead gives the same six error records ending in "OnTester critical error". On a live chart the same wrong path is not fatal: the tool stayed attached and retried, and the corrected path began measuring in place.
It says nothing about whether an indicator is profitable. A non-repainting indicator can still be useless, and some repainting indicators are used deliberately and correctly.
No trading functions, no DLL, no network access, no external files needed. It reads buffers and writes CSV files to MQL5\Files.
